## 0. 原則

| 環境 | 資料庫 | 連線方式 |
| --- | --- | --- |
| 本機開發 | SQLite 檔案（`backend/prisma/dev.db`） | `DATABASE_URL` → Prisma 預設 SQLite connector |
| 本機 D1 驗證 | miniflare 的本機 D1 | `wrangler --local` / `miniflare` |
| Production | Cloudflare D1 | Worker `env.DB` → `@prisma/adapter-d1` |

- **保留 Prisma ORM**，不改寫成手工 SQL。
- **保留本機 SQLite 的開發便利性** —— `npm run dev` / `npm test` 的流程完全不變。
- Worker 存取 D1 一律透過**原生 binding**（`env.DB`），**不使用 Cloudflare REST API**。

## 1. Prisma 版本：不需要升級

Cloudflare 官方文件明載 **「D1 is supported in Prisma ORM as of v5.12.0」**，本專案目前為：

| 套件 | 版本 | 狀態 |
| --- | --- | --- |
| `prisma` | `^5.21.1` | ✅ 已超過 5.12 門檻 |
| `@prisma/client` | `^5.21.1` | ✅ |
| `@prisma/adapter-d1` | `^5.21.1`（**本次新增**） | 版本需與 `@prisma/client` 對齊 |

**因此「最小必要版本升級」的結論是：不升級。** 這避開了 Prisma 6 的 breaking changes 與大規模 lockfile 變動，是風險最低的路徑。

唯一的 schema 變更是在 generator 加入 preview flag（driver adapters 目前**仍為 preview**）：

```prisma
generator client {
  provider        = "prisma-client-js"
  previewFeatures = ["driverAdapters"]
}

datasource db {
  provider = "sqlite"   // ← 不變。D1 本身就是 SQLite，provider 不需要改。
  url      = env("DATABASE_URL")
}
```

> `datasource` 與 6 個 model **一個字都沒有改**，因此 API 回傳的欄位與型別完全不變。

### 新增的相依套件

| 套件 | 類型 | 用途 |
| --- | --- | --- |
| `@prisma/adapter-d1@^5.21.1` | dependency | Prisma ↔ D1 binding |
| `@cloudflare/workers-types@^4` | devDependency | `D1Database` 型別 |
| `miniflare@^4` | devDependency | 本機 D1 測試 |

安裝：

```bash
cd backend && npm install
```

## 2. Database client abstraction

**取得 PrismaClient 的唯一入口是 `backend/src/db/client.ts` 的 `getPrisma(env)`。**
application layer 不得自行 `new PrismaClient()`。

```ts
export function getPrisma(env?: DatabaseEnv): PrismaClient {
  if (env?.DB) {
    // Workers：原生 D1 binding → adapter，不走 REST API
    return new PrismaClient({ adapter: new PrismaD1(env.DB) })
  }
  // Node：沿用 DATABASE_URL（本機 SQLite），process 內共用單例
  nodeClient ??= new PrismaClient()
  return nodeClient
}
```

| 呼叫端 | 寫法 | 結果 |
| --- | --- | --- |
| Express（Node） | `import { prisma } from './db.js'` | 行為與遷移前完全相同 |
| Worker | `import { getPrisma } from '.../db/client.js'` → `getPrisma(env)` | D1 |

`backend/src/db.ts` 維持原本的 `export const prisma`，因此 **`routes/`、`schemas/`、既有測試全部不需要修改** —— 這也是 API contract 得以維持的關鍵。

> ⚠️ Worker **不可** import `db.ts` —— 該檔案在 module 載入時就會建立 Node client，
> 而 D1 binding 只存在於 `fetch(request, env, ctx)` 的 `env` 中。
> Worker 請一律 import `db/client.js`。

**目前 `/api/*` 尚未遷移到 Worker（見遷移計畫 P6），因此 Worker 還沒有任何查詢會實際用到 `env.DB`。**
D1 這條路徑目前由 `backend/src/__tests__/d1.adapter.test.ts` 以 miniflare 驗證。

## 3. Schema 對 D1 / SQLite 相容性稽核

以下結論皆已在本機以真實 SQLite 引擎實測（執行 `migrations/0001_init.sql` 後驗證行為）。

| 檢查項 | 現況 | D1 相容 | 說明 |
| --- | --- | --- | --- |
| **id** | 6 個 model 全部是 `Int @id @default(autoincrement())` | ✅ | DDL 為 `INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT`，實測 id 正常遞增 |
| **DateTime** | `Profile.updatedAt`、`Experience.startDate/endDate`、`AdminUser.createdAt/updatedAt` | ✅ | ⚠️ 見下方「DateTime 儲存格式」 |
| **Boolean** | **完全未使用** | ✅ | schema 只用到 `TEXT` / `INTEGER` / `DATETIME` 三種欄位型別 |
| **relations** | 僅 1 組：`Skill.category → SkillCategory`（1:N） | ✅ | 巢狀 `include`（`GET /api/skills` 使用）實測正常 |
| **unique index** | `AdminUser.email @unique` | ✅ | `CREATE UNIQUE INDEX "AdminUser_email_key"`，實測重複插入被擋 |
| **foreign keys** | `Skill.categoryId → SkillCategory.id` | ✅ | 實測插入不存在的 `categoryId` 被 FK 擋下 |
| **cascade behavior** | `onDelete: Cascade` | ✅ | 實測刪除分類後底下技能一併消失 |
| **transaction** | **完全未使用**（無 `$transaction`） | ✅ | D1 不支援 Prisma interactive transaction，本專案剛好沒有任何依賴 |
| **enum-like fields** | **無 enum**。`sortOrder` 為 `Int @default(0)` | ✅ | SQLite / D1 本就不支援原生 enum |
| **raw SQL** | **完全未使用**（無 `$queryRaw` / `$executeRaw`） | ✅ | 無方言相依 |
| **Json 型別** | **未使用**。`contactLinks` / `highlightsZh` / `highlightsEn` / `techStack` 以 `String` 存 JSON | ✅ | 對 D1 高度友善，且 API 層的解析邏輯（`utils/json.ts`）完全不需改動 |

### ⚠️ DateTime 儲存格式（最容易踩的一點）

Prisma 的 SQLite connector 把 `DateTime` 存成 **epoch 毫秒的 INTEGER**，而不是 ISO 字串。已對實際的 `dev.db` 驗證：

```
AdminUser.createdAt   = 1789723044883   typeof = integer
Profile.updatedAt     = 1789730633895   typeof = integer
Experience.startDate  = 1690848000000   typeof = integer
```

**任何手寫的 seed / 匯入 SQL 都必須寫入整數**，寫成 `'2026-09-18T00:00:00Z'` 這種字串會讓 Prisma 讀回時解析失敗。
`scripts/d1-export-seed.ts` 已處理此轉換（`Date → .getTime()`）。

### FK enforcement

SQLite 需要 `PRAGMA foreign_keys = ON` 才會強制 FK；D1 預設啟用。本地以 SQLite 檔案開發時，Prisma 會自行開啟。若手動用 `sqlite3` CLI 檢查，記得自己下這個 pragma，否則會誤以為 cascade 沒生效。

## 5. Migrations

### 目錄

```
backend/migrations/0001_init.sql     ← wrangler d1 migrations 的來源
```

由 `wrangler.jsonc` 的 `d1_databases[0].migrations_dir` 指向。

> 刻意**不放在 `backend/prisma/migrations/`**：那是 Prisma Migrate 自己的目錄格式
> （`<timestamp>_<name>/migration.sql`），與 wrangler 的扁平 `.sql` 慣例不同，
> 混用會讓兩邊的 CLI 互相誤判。

### 產生 / 驗證 migration

`0001_init.sql` 是由現有 schema 具現而成的 baseline。要重新產生或驗證與 schema 一致：

```bash
cd backend
npm run d1:diff > ../tmp-check.sql
# 再與 migrations/0001_init.sql 比對
```

`d1:diff` 展開後為：

```bash
prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script
```

> ✅ `0001_init.sql` 已驗證：在乾淨 SQLite 上重複套用三次皆成功，且產生的 schema
> 與 Prisma 透過 `db push` 建立的 `dev.db` **逐字完全一致**（7 個 schema 物件全數比對通過）。

### 新增後續 migration

```bash
# 1. 產生帶編號的空檔
npx wrangler d1 migrations create idv-web add-something

# 2. 用 Prisma 算出差異 SQL，貼進該檔
cd backend
npx prisma migrate diff \
  --from-local-d1 \
  --to-schema-datamodel prisma/schema.prisma \
  --script
```

### 套用

```bash
# 本機（miniflare），可安全反覆執行
npm run d1:migrate:local

# 正式環境 —— 目前階段不應執行
npm run d1:migrate:remote
```

`wrangler` 會在 D1 中維護一張 migration 記錄表，**已套用過的檔案不會重複執行**，因此指令本身是冪等的。

### 不做自動 destructive migration

- `migrations/*.sql` **不得**包含 `DROP TABLE` / `DROP COLUMN`，除非是刻意規劃且已備份的變更。
- 本機的 `prisma db push --accept-data-loss`（`db:setup` 使用）**只作用於本機 dev.db**，永遠不會碰到 D1。
- seed 的清空動作被隔離在 `--reset` 旗標後（見下節），不會在 migration 流程中自動發生。

## 6. Seed

種子資料刻意拆成**兩個互不相干的部分**：

| 部分 | 產生方式 | 是否含 secret |
| --- | --- | --- |
| 內容資料（Profile / Skill / Experience / Project） | 由本機 SQLite 匯出 | 否 |
| 管理者帳號（AdminUser） | 由**環境變數**產生 | **是**（bcrypt 雜湊） |

兩者產生的檔案都放在 `backend/.generated/`，**已被 `.gitignore` 排除**。

### 6.1 內容資料

單一事實來源仍是 `prisma/seed.ts` —— 先把本機 SQLite 種好，再匯出，避免把 13 個分類 / 43 項技能手抄成 SQL。

```bash
cd backend
npm run db:setup          # 先確保本機 SQLite 內容正確
npm run d1:seed:sql       # → backend/.generated/d1-seed.sql

cd ..
npm run d1:seed:local     # 套用到本機 D1
```

- 預設**非破壞性**，只產生 `INSERT`，適用於全新的空 D1。
- 要重置既有資料需顯式加旗標：`npm run d1:seed:sql -- --reset`（會在前面加上 `DELETE`；**不含 AdminUser**）。
- 會保留原本的 `id`，確保 `Skill.categoryId` 的關聯正確。

### 6.2 管理者帳號（不得 hardcode）

```bash
cd backend
npm run hash-password -- "你的密碼"     # 產生 bcrypt 雜湊
# 貼到 .env 的 ADMIN_PASSWORD_HASH

npm run d1:admin:sql                    # 讀 ADMIN_EMAIL / ADMIN_PASSWORD_HASH
cd .. && npm run d1:admin:local
```

腳本行為：

- 從 `process.env` 讀取，**任何版控檔案中都沒有帳密**。
- 驗證 `ADMIN_PASSWORD_HASH` 確實是 bcrypt 格式（`$2a$10$...`，60 字元），填明碼會直接拒絕。
- 產生 `INSERT ... ON CONFLICT(email) DO UPDATE`（upsert）。

> 🔴 **安全性重點：`POST /api/admin/login` 只比對 `AdminUser` 表，完全不讀 `.env`。**
> 因此**更換 `ADMIN_EMAIL` 並不會停用舊帳號** —— 舊帳號連同其舊密碼雜湊仍然可以登入。
> 本機 `dev.db` 已經因此累積了 2 筆管理者（見 `CURRENT_ARCHITECTURE.md` §6.1）。
>
> 要讓新帳號**取代**而非**新增**，請使用：
>
> ```bash
> npm run d1:admin:sql -- --exclusive
> ```
>
> 它會在 upsert 之後刪除其他所有管理者帳號。

> ⚠️ `backend/.generated/d1-admin.sql` 內含密碼雜湊，**套用完請立即刪除**。

### 6.3 JWT secret

JWT secret **不屬於資料庫**，不會出現在任何 seed 檔。Production 以 Cloudflare Secret 注入：

```bash
wrangler secret put JWT_SECRET
```

絕不可寫在 `wrangler.jsonc` 的 `vars` 裡 —— 那是明文且會進版控。

## 7. Production D1

> ⚠️ **目前階段尚未建立任何 Cloudflare 資源。** 以下為建立時的步驟，非現在應執行的動作。

### 建立 database

```bash
npx wrangler d1 create idv-web
```

指令會回傳真實的 `database_id`。**必須**把它貼回 `wrangler.jsonc`：

```jsonc
"d1_databases": [
  {
    "binding": "DB",
    "database_name": "idv-web",
    "database_id": "00000000-0000-0000-0000-000000000000",  // ← 換成真實 id
    "migrations_dir": "backend/migrations"
  }
]
```

目前填的是**全零的佔位 UUID**：格式合法所以本機 `--local` 可以運作，但任何 `--remote` 操作都會明確失敗，避免誤觸不存在的正式資料庫。

### 初始化順序

```bash
npm run d1:migrate:remote                              # 1. 建表
wrangler d1 execute idv-web --remote --file=backend/.generated/d1-seed.sql    # 2. 內容
wrangler d1 execute idv-web --remote --file=backend/.generated/d1-admin.sql   # 3. 管理者
wrangler secret put JWT_SECRET                         # 4. secret
```

> 根目錄的 `package.json` **刻意只提供 `--local` 的 seed 指令**，正式環境的 seed 必須手動輸入完整指令，避免手滑。

## 8. Rollback / Backup 注意事項

### 🔴 先備份，再做任何 remote 操作

```bash
npx wrangler d1 export idv-web --remote --output=backup-$(date +%Y%m%d-%H%M).sql
```

D1 也提供 Time Travel（時間點還原，保留期依方案而定）：

```bash
npx wrangler d1 time-travel info idv-web
npx wrangler d1 time-travel restore idv-web --timestamp=<unix-timestamp>
```

### 注意事項

1. **migration 沒有自動 rollback。** wrangler 只往前套用，不會反向。要退版必須自己寫一支反向的 migration，或用 Time Travel 還原。
2. **先在本機演練。** 任何 migration 都應先 `npm run d1:migrate:local` 在乾淨的本機 D1 跑過。
3. **seed 的 `--reset` 是破壞性的。** 它會清空 Profile / SkillCategory / Skill / Experience / Project。正式環境執行前必先 export。
4. **`prisma db push --accept-data-loss` 永遠不要指向 D1。** 它只該用在本機 dev.db。
5. **Time Travel 不涵蓋 schema 誤刪的語意。** 還原的是資料庫狀態，但你的 `migrations/` 與 `schema.prisma` 不會同步回溯 —— 還原後記得檢查三者是否一致。
6. **上傳的圖片不在 D1 裡。** `avatarUrl` 只是字串路徑，實際檔案目前仍在 `backend/uploads/`（本階段未改動）。備份 D1 不等於備份圖片。

## 9. 本階段的測試

```bash
cd backend
npm run test
```

新增 `src/__tests__/d1.adapter.test.ts`，以 **miniflare 的真實 D1** 驗證：

| 測試 | 涵蓋的稽核項 |
| --- | --- |
| autoincrement 主鍵配發 | id |
| Profile 往返（含換行、單引號、JSON-as-String） | DateTime、字串跳脫 |
| Experience 的 DateTime 與 nullable endDate | DateTime |
| 巢狀 include（對應 `GET /api/skills`） | relations |
| `onDelete: Cascade` | foreign keys、cascade |
| `AdminUser.email` 唯一性 | unique index |
| `upsert` 兩次只留一筆 | seed 所依賴的操作 |

這些測試不觸碰任何本機 SQLite 檔案，可與既有的 supertest 測試並存。

### ⚠️ compatibility_date 的天花板

`wrangler.jsonc` 的 `compatibility_date` 與測試中的 `compatibilityDate` **都不得超過已安裝
workerd binary 支援的上限**，否則 runtime 會直接拒絕啟動：

```
MiniflareCoreError [ERR_RUNTIME_FAILURE]: The Workers runtime failed to start.
service core:user:: This Worker requires compatibility date "2026-09-18",
but the newest date supported by this server binary is "2026-08-06".
```

`wrangler dev` 也會撞到同一道牆。目前 `wrangler@^4` 帶的是 `workerd@1.20260730.1`，
上限為 **2026-08-06**，因此兩處都設為該日期。

升級 wrangler 後才可調高，且**必須兩處同步**：

| 位置 | 欄位 |
| --- | --- |
| `wrangler.jsonc` | `compatibility_date` |
| `backend/src/__tests__/d1.adapter.test.ts` | `compatibilityDate` |

查詢目前 binary 的上限：

```bash
npm ls workerd
```

> D1 的 SQL 語意完全不受這個日期影響 —— 它只決定 Workers runtime 的行為旗標。
